# 从需求到 POD：通用方法论与流程

> 本文从 careBalance（院衡）的完整产物链中抽象而来，剥离医院业务，保留可复用的工程方法。
> 适用于：以 FIN Framework / Haxall 为底座、以 Fantom Pod 形式交付的任何垂直行业应用
> （医院、工厂、园区、数据中心、供热站……）。
> 文中用 `xx` 代表你的新领域库前缀，`base` 代表被复用的底座库（careBalance 中分别是 `cb` 与 `em`）。

---

## 零 · 五条核心信条

这五条决定了后面所有流程的形状。先认同它们，流程才成立。

| # | 信条 | 反面教材 |
|---|---|---|
| 1 | **红线必须可被代码审计验证**，而不是只写在文档里 | "我们承诺不回写"——但代码里有 `updateXxx()` 方法 |
| 2 | **语义模型是地基，不是文档附件**。模型定完再写代码，模型改了要回写文档 | 先写表结构，Xeto 事后补 |
| 3 | **不确定性必须随数据流到 UI**，不得在中间层被抹平 | 后端知道这个数是估算值，前端只显示一个漂亮数字 |
| 4 | **组织工作决定排期，技术工作不决定排期** | 引擎写完了，但没有任何有效数据可以喂给它 |
| 5 | **每一期交付后系统必须能独立产生价值**，不能等全部上线 | 一期交付一堆半成品，客户看不到任何东西 |

## 一 · 全景：八个阶段与产物链

```text
P0 领域判定      →  复用边界表 · 差异分析表
     ↓
P1 业务方案 BP   →  BP 文档 · 汇报 PPT · 功能模块清单 · 指标体系 · 分期路线 · 配合事项清单
     ↓
P2 红线固化      →  N 条铁律 + 每条的九位落点矩阵
     ↓
P3 语义模型      →  lib/xx/*.xeto · 枚举表 · 点位规范 · 建模铁律
     ↓
P4 详细设计 DD   →  DD 文档 · 类图 · 时序图 · REST 契约 · 错误码全表 · 非功能指标
     ↓
P5 开发态展开    →  CLAUDE.md · docs/00~15 · 任务拆解（可直接开 issue）
     ↓
P6 编码与固化    →  Pod 代码 · CI 红线脚本 · 审计埋点
     ↓
P7 测试与验收    →  单元/集成/接口/验收四层 · 面向客户的验收标准表
     ↓
P8 分期交付      →  里程碑 D1~Dn · 阻塞风险表 · 组织依赖跟踪
```

**产物链的硬要求**：下游产物中的每一个元素，都必须能在上游找到出处；上游变更必须回写。
careBalance 的做法是在 `CLAUDE.md` 末尾明确写「本 docs/ 是上游文档的开发态展开，冲突时以本 docs/ 为准，并回写上游文档」——**冲突时以谁为准、以及回写义务，必须提前约定**。

## P0 · 领域判定与复用边界

**目标**：回答"这个项目到底要写多少代码"，并且用一张表把它固定下来。

### 动作 1：做结构性差异分析

不要一上来就列功能。先用 6~8 个维度，对比**新领域**与**底座已支持的领域**的结构性差异。careBalance 用的七个维度可直接借用：

| 维度 | 要问的问题 |
|---|---|
| 连续性 | 什么能停？什么绝对不能停？允许中断时间是多少量级？ |
| 介质/对象种类 | 底座支持的种类够不够？要新增哪几类？ |
| 负荷/行为曲线 | 底座的诊断阈值在这个领域还成立吗？ |
| 空间规则 | 空间边界由谁定义？是否与计量边界重合？ |
| 组织归属 | 成本算谁的？组织与空间是几对几？ |
| 考核口径 | 客户对外要交什么数？分母是什么？ |
| 合规环境 | 等保/行业规范/年检/审计，哪些是硬约束？ |

**产物**：差异分析表。每一行最后一列必须写「对系统的影响」——这一列直接生成后面的功能需求。

### 动作 2：画复用边界表（最重要的一张表）

逐条列出底座的全部能力，判定归属，并写明新领域的动作：

| 能力 | 归属 | 新域的处理 |
|---|---|---|
| 计量与点位 | base | 直接复用；只补领域专属点位 |
| 台账、关账、红冲 | base | 直接调用，**不改写** |
| 分摊 | base + xx | `XxAllocEngine extends BaseAllocEngine`，新增 N 段式与平衡断言 |
| 保障守门 | xx | 全新，底座无对应物 |
| …… | | |

**判定规则**（按优先级）：
1. 底座已有 → 直接复用，**禁止在新域另起一套**
2. 底座有但不够 → 继承扩展（`XxFoo extends BaseFoo`），不 fork
3. 底座能力确实不足 → **提 issue 改底座**，而不是在新域打补丁
4. 底座完全没有 → 新域全新实现

这张表的第二列决定工作量，第三列决定架构。它也是向客户/销售解释"为什么不是从零开发"的唯一凭据。

### 门禁（进入 P1 的条件）
- [ ] 差异分析表每行都有「对系统的影响」
- [ ] 复用边界表覆盖底座全部能力，无"待定"
- [ ] 明确写出**产品边界**：不做什么（careBalance: 不做 HIS、不做 HRP、不替代 BA 实时控制）

## P1 · 业务方案（BP）

**目标**：产出一份**业务视角**的文档，面向客户决策层与实施方，不含类图与接口签名。

### BP 的十章骨架（可直接套用）

| 章 | 内容 | 关键产出 |
|---|---|---|
| 1 | 产品定位与设计原则 | 一句话定位 · 三条设计铁律 · 与底座的关系 |
| 2 | 领域业务全景 | 角色地图 · 子系统划分 · 分级体系 · 业务闭环 · 结构特征 |
| 3 | 业务对象模型（业务语言，无字段） | **N 棵树 + 横切标签** |
| 4 | 功能模块设计 M1~Mn | 每模块：使用者 / 解决的问题 / 核心功能 |
| 5 | 指标体系 | 指标清单 · 计算式 · 分母来源 · 争议口径 |
| 6 | 关键业务场景 | 5 个左右高频剧本：痛点 / 平台做法 / 设计要点 |
| 7 | 落地约束与集成边界 | 网络分区 · 系统集成边界表 · 改造分级 |
| 8 | 实施路线与分期 | 每期：周期 / 模块 / 里程碑 / **验收标志** |
| 9 | 交付物与验收标准 | 六类交付物 · 可量化验收标准 |
| 10 | 风险与对策 | 每行：风险 / 影响 / 对策 |
| 附录 | 参数参考表 · 口径说明 · 外部接口清单 | |

### 三个必须做对的地方

**① 角色地图要标出"谁有否决权"**
careBalance 列了九类角色后写：「真正决定平台能否活下去的是三方：A 有一票否决权，B 决定结果是否被采信，C 决定考核能否推行。」
→ 通用做法：识别**否决者 / 采信者 / 执行者**三类关键角色，产品设计必须让这三方在系统里各自看到自己要的东西。

**② 对象模型用"N 棵树 + 横切标签"，不要压成一棵**
```text
空间树    回答：这个量用在哪里
组织树    回答：这个量算谁的账
系统树    回答：这个量属于哪个子系统，谁负责
计量树    回答：这个量从哪只表来，可信度如何
横切标签  回答：这里能不能动          ← 领域专属的关键增量
```
每棵树独立维护，通过引用关联。任一维度调整不会全盘重建。
**横切标签是垂直行业的核心增量**，务必单列一域。

**③ 分期原则要有内在逻辑，并说明"为什么某期不做某事"**
careBalance：先保障 → 后核算 → 再考核 → 最后优化。并明确写「一期不做分摊，因为分摊依赖计量改造与外部接口，二者都不是软件能独立决定的」。
→ 通用规则：**凡依赖外部组织工作的模块，一律后置**；一期只交付软件能独立完成、且客户每天都会用的东西，先建立存在感。

### 同步产出：汇报 PPT
BP 的压缩版，25 页左右。要点：
- 开篇不讲产品，讲**客户每年都要回答但答不利索的三个问题**
- 每条设计铁律后面必须跟一句「机制：XXX（第 N 页）」，把口号钉到具体页
- 有一页专讲**需要客户配合的 N 件事**（见 P8）
- 有一页专讲**数据主权与退出机制**（权限全开 / 接口三层 / 随时整库导出 / 不绑定厂商）
- 明确写"我们不承诺什么"（careBalance：不在签约前承诺具体节能率）

### 门禁
- [ ] 每个功能模块都有明确的使用者和"解决的问题"
- [ ] 每个指标都有分母来源和争议口径
- [ ] 分期表的每一期都有可量化的**验收标志**
- [ ] 风险表的对策中，需要客户配合的项已被提取

## P2 · 红线固化（本方法论的核心）

**目标**：把 BP 里的"设计铁律"从口号变成可执行、可审计、可测试的机制。

### 第一步：提炼 N 条红线

数量控制在 **5~7 条**。多了记不住，等于没有。写法必须是**祈使句 + 可判定**：

- ✅「平台永不写控制点。代码中不得出现向 `xxReadOnly` 对象写值的路径。」
- ❌「系统应保证安全性。」

careBalance 的七条可作为模板类型参考：
1. 某类对象**绝对只读**（安全边界）
2. 某类适配器**只读**（数据流向边界）
3. **数据最小化**（不取个案/敏感数据）
4. **内核不改写**（复用边界）
5. **算法顺序固定 + 平衡断言**（正确性边界）
6. **未核证的数默认降级口径**（可信度边界）
7. **N 类操作强制审计**（可追溯边界）

### 第二步：为每条红线填"九位落点矩阵"

**这是整套方法论最关键的一张表。** 一条红线如果不能在九个位置全部落地，它就是口号红线。

| 落点 | 问题 | careBalance 示例（红线①「永不写控制点」） |
|---|---|---|
| 1 模型位 | 语义模型里哪个标签/枚举承载它？ | `xxReadOnly: Marker`、`xxCareLevel: Enum` |
| 2 构造断言 | 领域对象构造时如何自校验？ | `CbCriticalArea` 构造断言：L1/L2 未置 `cbReadOnly` → 抛错 |
| 3 仓储校验 | 持久层如何拦截？ | `CbRepo` 写 `cbReadOnly` 对象直接拒绝，**不静默忽略** |
| 4 引擎机制 | 哪个引擎/算法实现它？ | `CbGuardEngine.check()` 三条硬规则 |
| 5 错误码 | 违反时返回什么码？ | `CB-2003`(403) / `CB-6003`(409) / `CB-6004`(422) |
| 6 API 行为 | 接口层如何表现？ | 写只读对象一律 `CB-2003`；判决本身是 200（业务结果非错误） |
| 7 UI 呈现 | 前端如何强制体现？ | L1/L2 详情页**不渲染**写操作入口（不是禁用，是不渲染） |
| 8 测试用例 | 哪几条测试守住它？ | `CbGuardEngineTest` 8 条 + `CbDomainTest` 5 条 |
| 9 CI 静态检查 | 如何自动化防回归？ | `check-no-point-write.sh` 扫描 `guard/` `engine/` 出现 `pointWrite` 即失败 |
| （10 审计） | 是否需要留痕？保留期？ | 判决无论通过否决一律写审计，保留 ≥5 年 |

再看红线②「适配器只读」的落点，验证矩阵的普适性：

| 落点 | 落地方式 |
|---|---|
| 契约 | `mixin XxReadOnlyAdapter { pull(span); ping() }` —— 只有这两个方法 |
| 数据结构 | `XxRawData` 字段清单不含任何敏感标识 |
| API | 相关接口只提供 GET 与内部拉取，**不提供任何写回端点** |
| 出方向 | 结果以**文件交付**，不直连写库、不提供 HTTP 推送 |
| 测试 | 反射扫描适配器全部方法名，出现写语义即失败 |
| CI | `grep -nE "(Void\|Obj) *(write\|post\|push\|update\|delete)[A-Za-z]*\("` 命中即 fail |
| 商务 | 作为对客户的书面承诺，且**承诺本身可被代码审计验证** |

> **这就是"红线可被代码审计验证"的完整含义**：不是让客户相信你，而是让客户（或第三方）能打开代码，用 grep 在 10 秒内验证你的承诺。

### 门禁
- [ ] 红线数量 ≤ 7
- [ ] 每条红线的九位落点矩阵填满，无空格
- [ ] 每条红线至少有 1 条 CI 静态检查或 1 组反射测试
- [ ] 红线写入 `CLAUDE.md` 第一屏（AI 编码代理与新人的第一份文档）

## P3 · 语义模型（Xeto lib）

**目标**：产出 `lib/xx/*.xeto`，作为整个 Pod 的地基。模型稳定之前不写引擎代码。

### 建模流程（五步）

**① 声明依赖顺序**
```text
sys → ph → ph.points → ph.equips → base → xx
```
`lib.xeto` 里显式声明。依赖顺序即抽象层次顺序，不得倒挂。

**② 枚举先行**
所有枚举集中在 `tags.xeto`，**每个枚举项必须写 `<doc:"...">`**。
枚举是业务共识的最小单元——枚举定不下来，说明业务没谈清楚，不要往下走。
careBalance 在 `tags.xeto` 里定了 13 个枚举，覆盖分级、子系统、类型、阶段、基数、来源、状态。

**③ 按域拆文件，一域一文件**
```text
lib.xeto        库声明与依赖
tags.xeto       全局标签、枚举、Choice
<域1>.xeto      组织
<域2>.xeto      横切标签域（关键区域 / 保障约束）  ← 领域核心增量
<域3>.xeto      子系统
<域4>.xeto      专属设备
points.xeto     专属点位
<域5>.xeto      业务量与口径确认单
mapping.xeto    外部编码映射                        ← 极易被遗漏，见下
<域6>.xeto      分摊与账单
<域7>.xeto      服务与工单
<域8>.xeto      资产
<域9>.xeto      应急/预案
```

**④ 写"建模铁律"（5~6 条）**
从 P2 的红线中，把属于建模层的部分单独抽出来，写在库 README 第一屏。例如：
- 某级别对象一律置只读标记
- 未会签的对象不参与任何策略校验
- 算法顺序不可调换，各段之和必须等于总量
- 只取聚合量，人工填报必须标来源等级
- 某约束必填依据文号，无依据不得生效
- 外部编码一律经映射层落地，未映射不丢弃

**⑤ 命名规约（一次定死，全局适用）**

| 类别 | 规则 | 示例 |
|---|---|---|
| Xeto spec | `Xx` + 大驼峰 | `XxCriticalArea` |
| Xeto 标签 | `xx` + 小驼峰 | `xxCareLevel` |
| Fantom 类 | `Xx` + 大驼峰 | `XxGuardEngine` |
| Axon 函数 | `xx` + 小驼峰 | `xxDeptAlloc` |
| REST 基址 | `/api/xx/v1` | 底座接口仍在 `/api/base/v1`，**不合并** |
| 错误码 | `XX-nnnn` | `XX-6003` |
| 权限点 | `xx:yyy` | `xx:guard` |

**规则**：凡底座或 `ph` 已定义的标签**直接复用，不得重定义**。

### 两个几乎总被遗漏的域

**① 外部编码映射域（`mapping.xeto`）**
只要要和客户的外部系统对账，就一定存在**多套编码并存且不同粒度**的问题。必须建独立映射层，四条约束：
1. 同一 `来源系统 + 外部编码` 在同一时刻只能有一组生效映射，生效期不得重叠
2. 一对多拆分时，同组比例之和必须为 1
3. 组织重组只**新增带新生效期的版本**，不修改历史映射 → 保证历史期可无损重算
4. 未映射编码**不丢弃**，进未映射池并保留数据；高层级指标照常产出，细粒度标注不完整

并且：**落库时同时保留原始外部编码 + 当时所用的映射版本引用**。
代价是多两个字段，收益是映射补齐后可按原始编码回溯重算，**不需要重新向外部系统取数**——外部历史数据导出往往要走审批，重取成本远高于多存两列。

**② 易被忽略的关键点位**
点表设计阶段必须专门盘一遍「日常几乎用不到、但监管检查/事故复盘时唯一有用」的量。
careBalance 的例子是柴发从启动到带载的实测时长——事后补测需要停电配合，代价极高。
→ 通用动作：让领域专家回答「出事之后，监管第一句会问什么数据？」，把答案全部列进点表。

- [ ] 所有枚举项有 doc
- [ ] 无重定义底座/`ph` 已有标签
- [ ] 建模铁律写入库 README
- [ ] 点表评审通过，含"事故复盘用"点位

### 引擎统一契约
```fantom
abstract const class XxEngine : BaseEngine {
```

### REST 契约总则（一次定死）

| 项 | 约定 |
|---|---|
| 基址 | `/api/xx/v1`，与底座接口并存不合并 |
| 鉴权 | 复用底座会话机制 |
| 时间 | ISO 8601 带时区 |
| 账期 | `span=2026-08` 或 `2026-08-01..2026-09-01`（左闭右开） |
| 分页 | `?page=&limit=`，响应头 `X-Total-Count`，limit 有上限 |
| 幂等 | 写接口必带 `Idempotency-Key`，缓存 24h，缺失即报错 |
| 排序 | `?sort=-ts,val` |
| 错误 | HTTP 状态 + `{"error":{"code","msg","detail"}}`，**不暴露堆栈** |
| 数据范围 | Principal 携带 scope，越权返回专用错误码并写审计 |
| 只读保护 | 写只读对象一律报错，**不静默忽略** |
| 业务判决 | 判决类结果（通过/否决）一律 **HTTP 200**，判决本身是正常业务结果 |
| 长任务 | `202 {jobId}` + 轮询进度接口 |

### 错误码全表（必须在 DD 阶段一次定完）
- 格式 `XX-nnnn`，与底座错误码**前缀区分、编号空间不合并**
- 按段分配：`1xxx` 参数 / `2xxx` 权限 / `3xxx` 核心算法 / `4xxx` 外部数据与映射 / `5xxx` 口径 / `6xxx` 红线与守门 / `7xxx` 工单 / `8xxx` 资产 / `9xxx` 调度与应急
- 每行四列：**码 · HTTP · 含义 · 处置建议**。"处置建议"这一列是给现场实施人员的，不能省
- 所有对外异常统一收敛为一个 `XxError` 类型，携带 `code / msg / detail / httpStatus`

### 非功能设计：容量估算要写"计算式"
```text
计量点位     1,200 只表 × 5             = 6,000 点
关键区域点位 120 区域 × 8               =   960 点
子系统点位   估算                        ≈ 2,000 点
点位合计                                 ≈ 8,960 点
历史写入     8,960 × 96（15 分钟粒度）   = 860,160 条/日
```
并明确标注「**所有数值为按公式推算的工程估算值，需在集成测试阶段以压测结果修正**」。
性能目标表同样标注「规划值，待压测验证」。→ 通用规则：**估算值必须标记为估算值**，这是信条 3 在文档层的体现。

## P6 · 编码与红线固化

### 编码规范要点（Fantom / Haxall 场景）

| 主题 | 规则 |
|---|---|
| 类与文件 | 一个文件一个公开类，文件名与类名一致 |
| 不可变性 | 领域对象一律 `const class`；修改通过构造新实例 + commit |
| 引擎状态 | 引擎不得持有可变状态；上下文经 `CalcCtx` 显式传入 |
| 必填 vs 可选 | 必填用 `rec->field`（缺失即抛），可选用 `rec["field"]` |
| 异常收敛 | 对外可见的校验失败一律转成 `XxError`，底层异常不得漏到 HTTP 层 |
| 日志 | 每引擎持 `Log`，命名 `xx.engine.<name>`；红线级事件 `log.warn` **且同时写审计** |
| 并发 | 重计算一律经统一 Scheduler（Actor）串行化，不自建 Actor 池 |
| 阻塞 | 禁止在 Actor 消息处理中做阻塞 IO 超过 30s；长任务拆批并回写进度 |

### 提交规范
```text
<type>(<scope>): <subject>
type:  feat | fix | refactor | test | docs | chore
scope: xeto | domain | engine | <核心域> | api | axon | adapter | ui
```
**附加规则**：涉及核心算法的改动，PR 描述必须说明**对历史账期重算结果的影响**。

### CI 红线脚本（每条红线至少一条）
```bash
# 示例 1：只读适配器静态检查
grep -nE "(Void|Obj) *(write|post|push|update|delete)[A-Za-z]*\(" \
     fan/adapter/XxAAdapter.fan fan/adapter/XxBAdapter.fan \
  && { echo "FAIL: 只读适配器中发现写方法"; exit 1; } || exit 0

# 示例 2：核心链路禁止写点位
grep -rn "pointWrite" fan/guard/ fan/engine/ \
  && { echo "FAIL: 守门链路中发现 pointWrite"; exit 1; } || exit 0
```
CI 完整清单：
```bash
fan test <podName>                          # 单元 + 集成
xeto lint lib/xx                            # 语义库
bash scripts/check-readonly-adapter.sh      # 红线②
bash scripts/check-no-point-write.sh        # 红线①
```

### 幂等与事务补偿（Folio 无跨 rec 事务时的通用模式）
```fantom
Str idempotencyKey(Str op, Ref siteRef, Span span, Granularity g) {
  Buf().print("$op|$siteRef|$span|$g").toDigest("SHA-1").toHex
}
```
```text
1  按批提交，每批 N 条，记录批次游标
2  任一步骤失败：
     已提交批次不做物理删除
     逐批生成"红冲"（反向）条目撤销
     周期状态标记 failed
3  重新发起时按新的幂等键执行
```
**原则：任何中间态都可审计。** 不做物理删除，用反向条目撤销——与账务红冲机制一致。

### 审计埋点
在 P2 确定的 N 类强制审计操作，每一处都必须写：`actor / op / target / before / after / ts`。
`after` 中要包含**当时的实测值与判据**，而不只是结论——事后复盘时结论没用，判据才有用。

## P7 · 测试与验收

### 四层测试

| 层 | 工具 | 范围 |
|---|---|---|
| 单元 | 语言内置 Test | 领域不变式、核心算法、解析逻辑 |
| 集成 | Test + 测试 Folio | 全链路：取数 → 归一 → 关账 → 计算 → 出结果 → 异议 → 会签 |
| 接口 | HTTP 用例集 | REST 契约、错误码、幂等 |
| 验收 | 现场 | 见下 |

### 单元测试的来源
**直接来自 P5 各算法文档末尾的「必测用例」表**，不额外发明。
额外必测的三类：
1. **领域不变式**：每个构造断言一条用例
2. **红线拦截**：每个红线错误码一条用例（写只读对象、缺依据文号、非法状态流转……）
3. **反射类检查**：适配器方法名扫描、数据结构字段清单扫描

### 集成测试
写**一条完整主链路**测试，串起所有引擎。careBalance 的 `CbCloseFlowTest`：
> 造测试数据 → 取数 → 映射 → 关账 → 分摊 → 出账单 → 算指标 → 发起异议 → 会签处理
>
> 断言：结果可下钻到最小单元；缺口率 < 阈值时可关账，> 阈值时阻断。

### 验收标准（面向客户，写进合同）
**验收看结果，不看功能清单打勾。** 每条必须可量化、可在现场当场验证：

| 类型 | 模板 |
|---|---|
| 数据完整性 | 核心点位连续采集 N 天，数据完好率 ≥ X% |
| 账目可信度 | 完成至少一个完整周期关账，缺口率 < X%，且缺口量独立呈现未摊入任一对象 |
| 结果可采信 | 客户方 XX 部门**书面确认**结果可用于 YY；每份结果可下钻至最小单元 |
| 指标可产出 | 两项核心指标由平台自动产出，口径经客户确认 |
| 流程闭环 | 线上闭环率 ≥ X%，时效统计可用于考核 |
| 权限与审计 | 客户获得全部管理权限；N 类强制审计操作可追溯 |

注意「**书面确认**」这三个字——验收标准里凡涉及主观采信的，必须落到书面。

## 二 · 贯穿全程的六条通用工程规则

这六条不属于任何单一阶段，而是在每个阶段都要检查。

### 规则 1 · 数据可信度必须三态化并流到 UI

任何计算结果都要携带出处标记，且**中间层不得抹平**：

| 层 | 机制 |
|---|---|
| 模型 | `dataSource`（实测/推导/分摊/估算/人工）、`confirmed`、`verifyStatus`、`coverage` |
| 引擎 | 分母未确认 ⇒ 结果仍产出，但标记 `reference = true` |
| API | 响应中必须带 `reference` / `verifyStatus` / `directRatio` 等标记字段 |
| UI | **强制渲染规则**：非 verified 一律渲染徽标；`reference==true` 必须渲染「参考值」徽标并在 tooltip 显示来源；覆盖率低于阈值以警示色呈现 |

careBalance 前端有专门一节叫「强制渲染规则」，写着：
> 前端不是只负责好看，以下四条是产品约束的最后一道呈现保障。

其中第 4 条尤其值得学：**只读对象不得渲染任何写操作入口——不是禁用，而是不渲染。**

### 规则 2 · 每个外部依赖必须有代码层降级分支

```fantom
XxRawData[] pullSafe(Span span) {
  try return external.pull(span)
  catch (Err e) {
    log.warn("外部系统不可达，切人工填报兜底", e)
    audit("data.fallback", span)
    return repo.readManualData(span)   // dataSource = manual, confirmed = false
  }
}
```
三条要求：① 不中断整体流程 ② 写审计 ③ 受影响结果自动降级标注。
**降级路径写进代码，而不是写进运维手册。**

### 规则 3 · 不丢弃原始输入，保留转换版本引用

任何经过映射/归一/换算落库的数据，同时记录：**原始外部键 + 当时所用的转换规则版本引用**。
收益：规则修正后可按原始键**回溯重算**，不需要重新向外部系统取数。
成本：多两个字段。这个交易永远划算。

### 规则 4 · 默认值一律朝安全方向取

| 情形 | 错误做法 | 正确做法 |
|---|---|---|
| 读不到实测值 | 当作没问题，放行 | **视为不满足**，拒绝 |
| 找不到所属分级 | 按最低级别处理 | **按最高级别保守拒绝** |
| 约束缺依据 | 仍然生效 | 不得生效 |
| 写只读对象 | 静默忽略 | **明确报错**（便于发现异常调用） |

最后一条尤其重要：**静默忽略会掩盖调用方的 bug**，明确报错才能暴露它。

### 规则 5 · 顺序型算法必须有平衡断言

凡是"多段/多阶段拆分总量"的算法：
1. 顺序在枚举中固化，代码中按枚举顺序调用，**不可调换**
2. 最后一步 `assertBalance()`：各段之和 == 总量（带明确容差，如 0.01%）
3. 不通过即**抛错并阻断后续事务**，不是警告
4. 不参与分摊的部分（缺口量）以**独立虚拟对象**保留，永不摊入
5. 上限提示（如单对象占比超阈值）**仅提示，不阻断**——区分"错误"与"质量问题"

### 规则 6 · REST 与脚本函数共享引擎实现

```text
XxRestMod ─┐
           ├─→ XxEngine（唯一实现）
XxAxonFuncs┘
```
**不存在两套逻辑。** Axon 函数只是引擎的另一个门面，签名与 REST 对应。
额外收益：现场实施人员可以用脚本直接调用同一逻辑做排查和批处理。

## 四 · 常见失败模式与对策

| 失败模式 | 症状 | 对策（对应阶段） |
|---|---|---|
| 红线口号化 | 文档写了"不回写"，代码里有写方法 | P2 九位落点矩阵 + P6 CI 脚本 |
| 从零开发幻觉 | 底座能力重复实现，工期翻倍 | P0 复用边界表 + "底座不足则改底座"规则 |
| 模型事后补 | 先写代码后补 Xeto，两者不一致 | P3 门禁：模型稳定前不写引擎 |
| 忘记映射层 | 外部编码直接当主键用，重组后历史全乱 | P3 必建 `mapping.xeto` + 保留原始键 |
| 排期按技术依赖 | 核心引擎先写好，无数据可喂，空转 | P8 组织依赖优先排序 |
| 客户配合无兜底 | 外部接口不通，整个指标体系停摆 | P1 配合事项清单必填兜底方案 + 规则 2 |
| 不确定性被抹平 | 估算值在 UI 上和实测值长一样 | 规则 1 三态化 + 前端强制渲染规则 |
| 静默忽略 | 非法写操作被吞掉，bug 潜伏数月 | 规则 4 明确报错 |
| 验收清单化 | 功能全打勾但客户不认账 | P7 可量化验收标准 + 书面确认 |
| 文档与代码漂移 | docs 说一套代码写一套 | P5 约定"冲突时以 docs 为准，并回写上游" |
